01

コミットはバックアップではない

最初に、一番損をしやすい誤解から潰します。Gitを使い始めた人の多くが 「コミットした＝保存された＝安心」と考えます。これは違います。

コミットで記録が書き込まれる先は、作業しているフォルダの中にある .git という隠しフォルダです。つまり同じPCの、同じディスク。

保管場所
作業中のファイル   C:\Users\あなた\プロジェクト\
履歴（.git）       C:\Users\あなた\プロジェクト\.git\   ← ここに記録が溜まる
                                                 同じフォルダ・同じディスク

だから、コミットが守ってくれる範囲はここまでです。

起きたことコミットだけの状態
ファイルを間違えて消した助かる　履歴から復元できる
変な編集をして壊した助かる　前の時点に戻せる
「3日前はどう書いてた？」わかる　全部残っている
SSDが物理的に壊れた全滅　履歴も一緒に消える
PCを落とした・盗まれた全滅　履歴も一緒に消える
ランサムウェアで暗号化された全滅　履歴も暗号化される
所見

コミットが効くのは自分の操作ミスだけです。ハードウェアの故障には無力です。 バックアップの原則は「別の物体に置く」—— 同じディスクの中に何個コピーを作っても、それはバックアップとは呼びません。

外部に置いて初めてバックアップになります。その「外部」の代表がGitHubで、 送る動作が push です。ここが次章の話につながります。

02

GitとGitHubは別物

名前が似ているせいで、ほぼ全員がここを混同します。そして 「Gitを使う＝ネットに公開される」と誤解して、手を出さなくなります。

Git ＝ PCの中だけで動く、記録装置

ネットに一切つながっていません。どれだけコミットしても、外には出ません。 電源を抜いた状態でも動きます。Gitは通信しないソフトです。

GitHub ＝ そのコピーを預けるクラウド倉庫

Microsoftが運営するサービスです。Gitの履歴を丸ごと預かってくれます。 ここに送って初めてネット上に置かれます。 そして送るとき、誰に見せるかを選べます。

結論

「公開は嫌、でも保存したい」＝ private リポジトリに push する。 これで両立します。矛盾しません。

03

公開されないための設定

GitHubに置く保管庫をリポジトリと呼びます。1プロジェクト＝1リポジトリです。 作るときに公開設定を選びます。

設定誰が見られるか使いどころ
private 🔒 自分と、招待した人だけ 仕事・原稿・商品・個人の資産。迷ったらこちら
public 🌐 全世界。検索にも出る 公開したいWebページ、配布したいツール

private はどこまで見られないか

  • 検索エンジンに出ません。URLを知っていても他人はアクセスできません（404が返ります）
  • 見られるのは自分のアカウントと、自分が招待した人だけです
  • 無料アカウントでも private は無制限に作れます
補足

「privateは有料」という情報が今も出回っていますが、これは2019年より前の話です。 現在は無料で無制限に作れます。古い記事を読んで諦める必要はありません。

やってはいけない

一度 public にしたものを private に戻しても、公開中に誰かがコピーした分は取り消せません。 public への切り替えは、内容を全部確認してからにしてください。 通常は「最初から private で作り、ずっと private のまま」で問題ありません。

04

覚える動作は4つだけ

Gitのコマンドは百個以上ありますが、日常で使うのは4つです。 残りは困ったときにAIに聞けば足ります。

動作意味たとえると公開？
git add 記録する対象を選ぶ カルテに書く項目を選ぶ されない
git commit 「この時点」を刻む 日付を入れて署名する されない
git push GitHubへ送る＝保管完了 控えを外部倉庫に預ける privateならされない
git pull GitHubから取り込む 倉庫の最新版を持ち帰る —

もう1つ、コマンドではありませんが最も使うのが git status です。 「今どうなってる？」を確認するだけで、何も変更しません。迷ったらこれを打つと覚えてください。

日々の流れ
git status          # 今どうなってる？（何も変えない・安全）
git add -A          # 変更を全部、記録対象にする
git commit -m "何をしたか"
git push            # ← ここまでやって初めてバックアップ
所見

add と commit はセットで1つの動作だと考えて構いません。 初心者が意識すべき境界は「commitまで」と「pushした」の間です。 ここが、消えるか残るかの分かれ目です。

05

いつコミットし、いつ push するか

コマンドを覚えても、次に必ず詰まるのがここです。 「どのタイミングで、どのくらいの粒度でやればいいのか」—— 教科書に書いていないので、自己流のまま溜め込んでしまいます。

コミットの基準は、たった一つ

判断基準

「ここまで戻れたら嬉しい」と思った瞬間にコミットする。
これだけです。完成している必要も、きれいである必要もありません。 戻りたくなる可能性のある地点に、しおりを挟む——それがコミットです。

「まだ途中だからコミットしない」は逆です。途中だからこそ挟んでおく。 この後の変更で壊しても、しおりの地点に戻れます。

コミットする具体的なタイミング

場面コミットなぜ
1つの作業が区切りまで進んだ する 記事を1本書き終えた、ナレッジを5件足した、設定を変えて動いた
これから大きく書き換える 直前にする 壊す前に安全地帯を作っておく。最も効くタイミング
AIに大きな作業を頼む前 する 結果が気に入らなければ、丸ごと戻せる状態にしておく
試行錯誤がうまくいった すぐする 「さっきの方が良かった」を後から取り返せる
今日の作業を終える する 中途半端でも構わない。翌日の自分への引き継ぎになる
1文字だけ直した まとめてよい 刻みすぎても害はないが、意味の単位で束ねる方が後で読みやすい
粒度の目安

「このコミットは何をしたか」を一言で言えるなら、粒度は正しいです。 「あれとこれと、あと……」となったら大きすぎます。 とはいえ大きすぎて壊れるものではないので、迷ったらそのままコミットして進んで構いません。

コミットメッセージは、未来の自分への手紙

-m の後に書く一言です。読むのは半年後の自分だけなので、 形式にこだわる必要はありません。ただし中身は要ります。

例評価
避ける update　修正　aaa　作業 半年後の自分が何も思い出せない
よい 腰痛記事の導入を書き直し 何をしたかが1行でわかる
よい 介護観察GPTに事例5件追加 対象と量が具体的
さらによい 算定表の集計式を修正（13単位の上限が効いていなかった） なぜが書いてある。理由はコードから読み取れない

コツは「何を」より「なぜ」を書くことです。何をしたかは記録から読み取れますが、 なぜそうしたかは書いておかないと永久に失われます。

push のタイミング

コミットと違い、push は「安全な場所に移す」動作なので、基準が変わります。

タイミング優先度理由
その日の作業を終えたとき 原則 失っても1日分で済む。これが基本形
最低でも週に1回 下限 これを超えて溜めると、確認も復旧も重くなる
PCを持ち出す前・出かける前 必須 紛失・盗難・破損が現実に起きうる瞬間
大きな作業に取りかかる前 必須 手元が壊れても、外部に無傷の控えが残る
別のPCで続きをやりたいとき 必須 push しないと、もう一方のPCから取り出せない
1時間おき 不要 やっても害はないが、そこまでの頻度は要らない
溜めることの危険

push を溜めると、失うものが増えるだけではありません。 いざ送るときに「中身を覚えていない」状態になります。 機密が混ざっていないか確認しようにも、100件を超えると現実的に見きれません。 こまめに送るのは、安全確認を可能にするためでもあります。

1日の流れに落とすと

典型的な1日
朝  作業を始める前
git pull                          # 別の場所での変更を取り込む

昼  記事を1本書き終えた
git add -A
git commit -m "腰痛記事の第2稿を執筆"

昼  大きな書き換えに入る前
git commit -m "構成変更前の状態"    # ← 安全地帯を作る

夜  作業終了
git add -A
git commit -m "構成を3幕に変更・CTAを差し替え"
git push                          # ← ここでバックアップ完了
迷ったときの原則

コミットも push も、多すぎることによる害はありません。 少なすぎることだけが害になります。 迷ったらやる——それで間違いになる場面は、実質ありません。

06

ブランチ＝作業の分身

本の執筆で考えてください。原稿があって「第3章を大きく書き直したい。でも失敗したら元に戻したい」。 そういうとき、原稿をコピーして別冊で書き直しますよね。それがブランチです。

構造
main（本編）──●──●──●──●──●     ← いつでも読める完成版
                    │
                    └──●──●       ← 別冊。ここで実験する

うまくいったら本編に取り込む。これが統合（merge）。 失敗したら別冊ごと捨てる。本編は無傷です。

なぜAIツールが勝手にブランチを作るのか

Claude CodeやCodexに作業を頼むと、claude/なんとか のような名前のブランチが 増えていることがあります。あれは「本編を汚さないよう別冊を作った」結果です。 勝手に増えているように見えて、実は安全のための動作です。

覚え方

main（またはmaster）は本編。それ以外は全部別冊です。 今どの冊にいるかは git status の1行目でわかります。

07

統合と、衝突

別冊を本編に取り込む操作が merge（マージ・統合）です。 どちらも消えません。両方の変更が残ります。

枝分かれは、こうして起きる

初心者が最初に遭遇する事故がこれです。原因はほぼ1パターンに決まっています。

原因

PCで作業 → pushせず放置 → ブラウザでPRの「Merge」を押した。 片方だけが進むと、必ず枝分かれします。 防ぎ方は1つ、ブラウザでマージしたら当日中に git pull です。

コンフリクト（衝突）とは

統合で唯一やっかいなのがこれです。同じファイルの同じ行を、両側が別々に書き換えているとき、 Gitは「どちらを採用すべきかわからない」と止まります。

逆に言えば、触ったファイルが重なっていなければ衝突しません。 別のフォルダで作業していた場合などは、Gitが自動で全部やってくれます。

統合する前に、必ず予行演習する

衝突するかどうかは、実行前に調べられます。作業中のファイルに一切触らずに試せるコマンドがあります。

予行演習（作業ツリーを変更しない）
git merge-tree --write-tree 今のブランチ 取り込みたいブランチ

# 終了コード 0 → 衝突なし。安心して統合できる
# 終了コード 1 → 衝突あり。件数と場所が表示される

これを知らないと「やってみないとわからない」と身構えることになります。 統合の可否は、実行前に判定できると覚えておいてください。

もし衝突したら

慌てなくて大丈夫です。git merge --abort で完全に元通りになります。 統合は「足す」操作なので、失敗しても引き返せます。

08

PRとは何か

PR（プルリクエスト）＝「この別冊を本編に取り込んでいいですか？」という申請書です。

merge はコマンド一発で即座に統合します。 PRは、その統合の手前に確認の場を挟む仕組みです。

流れ
別冊ブランチで作業
      ↓
PRを出す      「こう変えました。取り込んでいいですか？」
      ↓
［ 確認の場 ］  変更点が1行ずつ色分けで見える
              コメントを書ける／レビューできる
              テストが自動で走る
      ↓
「Merge」ボタンを押す
      ↓
本編（main）に統合される

つまり PR ＝ merge ＋ 確認画面 ＋ 記録 です。 番号（#1, #2）が振られ、議論が永久に保存されます。

一人で使う意味はあるか

本来はチーム開発の道具です。「勝手に本編を書き換えられたら困る」ので他の人が目を通す。 ただし一人でも無意味ではありません。変更点を落ち着いて見返せて、 「なぜこの変更をしたか」が記録として残ります。

落とし穴

PRを開いたまま放置すると、内容ではなく前提が古くなります。 2週間放置したPRが、その間に別の整理と食い違って49件の衝突を起こす—— といったことが普通に起きます。 PRは出したら数日以内に処理する。無理なら閉じて、必要になったら作り直す方が速いです。

09

入れてはいけないもの

ここは医療・介護の仕事をしている人にとって、技術的な話より重要です。

絶対に入れないもの

  • 患者を特定できる情報（氏名・カルテ番号・生年月日と紐づく記録・写真）
  • APIキー・トークン・パスワード（.env ファイルなど）
  • 個人が特定できる第三者の情報全般
最重要

一度コミットしたものは、あとでファイルを消しても履歴に残ります。 「間違えて入れた → 削除した」では消えません。private であっても、倉庫の中には残り続けます。 入れる前に止めるのが、唯一の確実な対策です。

.gitignore ——「これは記録しない」リスト

プロジェクトの一番上に .gitignore という名前のテキストファイルを置くと、 そこに書いたものはGitが無視します。

.gitignore の例
# 認証情報
.env
.env.*

# 個人情報を含む出力
output/patients/
# 自動生成物・巨大ファイル
node_modules/
*.log
*.tmp
*.sqlite
重要な制限

.gitignore は「これから追加するファイル」にしか効きません。 すでにコミット済みのファイルは、あとから書き足しても除外されません。

今後の記録だけ止めたい場合は git rm --cached ファイル名 を使います。 PCのファイル自体は消えませんが、過去の履歴にはやはり残ります。

だから

最初のコミットの前に .gitignore を作ってください。 順番を逆にすると、あとから取り返すのが非常に面倒になります。 これが導入時に一番効く一手です。

10

導入手順（ゼロから初回保管まで）

Windowsを前提に、実際に手を動かす順に並べます。全部で30分ほどです。 1つずつ、AIに聞きながらで構いません（頼み方は次章）。

  1. 1

    Gitをインストールする

    git-scm.com からWindows版をダウンロードして実行します。 選択肢がたくさん出ますが、全部そのまま「Next」で問題ありません。

    終わったらPowerShellを開いて確認します。

    確認
    git --version
# git version 2.xx.x のように出れば成功
  2. 2

    名前とメールアドレスを登録する

    誰が記録したかを残すための設定です。1回だけやれば以降ずっと有効です。 このメールアドレスはコミットに埋め込まれますので、 public なリポジトリを作る予定があるなら公開して問題ないものにしてください。

    初回のみ
    git config --global user.name "あなたの名前"
git config --global user.email "あなたのメール"
  3. 3

    GitHubのアカウントを作る

    github.com で作成します。無料で構いません。 二段階認証（2FA）は必ず有効にしてください—— 大事な資産の保管庫になるためです。

  4. 4

    GitHub CLI を入れて、ログインする

    認証はGitの初心者が最もつまずく箇所です。 GitHub CLI（gh）を使うと、この面倒を丸ごと回避できます。 ブラウザが開いてログインするだけで済みます。

    PowerShell
    winget install --id GitHub.cli

# インストール後、PowerShellを開き直してから
gh auth login
# → GitHub.com / HTTPS / Login with a web browser を選ぶ
  5. 5

    .gitignore を先に作る

    この順番が肝心です。コミットより前に作ります。 保管したいフォルダの直下に、.gitignore という名前で作ってください。 中身は第9章の例をそのまま使えます。

    何を除外すべきか迷ったら、この時点でAIに「このフォルダを見て、 .gitignore に入れるべきものを挙げて」と頼むのが確実です。

  6. 6

    記録を開始する

    保管したいフォルダで、Gitの管理を始めます。

    プロジェクトのフォルダで
    cd C:\Users\あなた\プロジェクト

git init                     # このフォルダの記録を開始
git add -A                   # 全部を記録対象に
git commit -m "最初の記録"
  7. 7

    GitHubに private の倉庫を作って、送る

    gh を入れてあれば、倉庫の作成とpushが1行で終わります。 --private を必ず付けてください。

    作成と初回push
    gh repo create 好きな名前 --private --source=. --remote=origin --push
    確認

    最後に必ず、本当に private になっているか自分の目で見てください。

    検証
    gh repo view --json isPrivate,visibility
# {"isPrivate":true,"visibility":"PRIVATE"} なら成功
  8. 8

    2回目以降は、3行だけ

    ここまで来れば、日々やることはこれだけです。

    日常
    git add -A
git commit -m "何をしたか一言"
git push
11

AIと相談しながら進める

Gitはコマンドを覚えるより、「何が起きているか」を読み取る力の方が重要です。 そこはAIが得意な領域なので、任せてしまって構いません。 ただし任せ方に線引きがあります。

まず、この一言から始める

Claude Code のようにファイルを読めるAIなら、状況を自分で調べてくれます。 コマンドを教えてもらうのではなく、状況を説明してもらうのが正しい使い方です。

頼み方の型
「今のGitの状態を調べて、初心者にわかるように説明して。
　まだ何も実行しないで。」

「まだ実行しないで」を付けるのがコツです。 先に説明させ、内容を理解してから実行を頼む。この2段階にすると事故がほぼなくなります。

場面別の頼み方

やりたいことそのまま使える依頼文
バックアップしたい 「バックアップして。機密情報が混ざっていないか先に確認して、結果を見せてから進めて」
導入したい 「このフォルダをGitで管理したい。.gitignore に入れるべきものを先に挙げて」
エラーが出た 「このエラーの意味と、なぜ起きたかを説明して。対処は提案だけして、実行しないで」
操作が怖い 「この操作は取り消せる？ 取り消せない？ 先に教えて」
散らかってきた 「ブランチの状況を整理して見せて。どれが使われていて、どれが放置か」
統合したい 「統合したい。先に予行演習して衝突件数を出してから判断させて」

AIに任せてよい／確認すべき の線引き

種類例判断
読むだけ status log diff merge-tree 任せてよい　何も変わらない
足すだけ add commit merge 任せてよい　引き返せる
外部に出す push PRの作成・コメント 内容を見てから承認する
書き換える rebase --force reset --hard clean -fd 必ず止める　説明を求める
この4語が出たら手を止める

--force　reset --hard　clean -fd　filter-repo

これらは記録そのものを消したり書き換えたりします。 AIが提案してきたら、実行する前に「なぜそれが必要か、他に方法はないか」と聞き返してください。 大抵は、もっと安全な代替手段があります。

仕組みで防ぐ

Claude Code を使っているなら、危険なコマンドを実行前にブロックする設定を入れられます。 人間の注意力に頼らずに済むので、導入をおすすめします。

Claude Code で
/git-guardrails-claude-code

push や reset --hard などを、実行される前に止めるフックを設定してくれます。

大前提

Gitで本当に失われるものは、ほとんどありません。 一度コミットしてさえいれば、大抵の失敗は復元できます。 怖いのは「コミットしていない変更」と「上のリストの4語」だけです。 この2つを避けている限り、思い切って触って構いません。

12

詰まったときの対処

初心者が遭遇する順に並べます。どれも壊れてはいません。

「rejected」と言われて push できない

GitHub側に、自分が持っていない変更があります。第7章の枝分かれです。 git pull で取り込んでから、もう一度 push してください。

やってはいけない

ここで git push --force を使うとGitHub側の変更が消えます。 検索するとこの解決策が出てきますが、初心者は使わないでください。

コンフリクトが出て止まった

git merge --abort で完全に元に戻せます。落ち着いてから、 AIに「衝突の内容を説明して。どちらを残すべきか判断材料をください」と頼んでください。

間違ったファイルをコミットしてしまった

まだ push していなければ、比較的簡単に取り消せます。 push する前に気づくことが分かれ目なので、機密が関わるものは コミット前に git status で一覧を確認する習慣をつけてください。

ファイルが消えた気がする

一度でもコミットしていれば、まず残っています。 AIに「このファイルの履歴を調べて、最後に存在したコミットを教えて」と頼めば見つかります。

ブランチが増えすぎてわからない

放っておいても害はありません。整理したくなったら 「使われていないブランチを一覧にして。それぞれ最終更新日と、統合済みかどうかも」 と頼んでください。削除は、確認してから一つずつで構いません。

2.2GBもある。重すぎないか

.git フォルダが大きいのは、履歴を全部持っているからです。異常ではありません。 ただし100MBを超えるファイルはGitHubが受け付けません。 動画や大きなデータは .gitignore で除外し、別の方法で保管してください。

13

週次ルーティン

最後に、これだけ守れば十分という運用をまとめます。 理想は週1回。溜めるほど確認が重くなります。

タイミングやること理由
週に1回 git status を見て、溜まっていたら commit → push 1週間分なら中身を覚えている。確認できる
ブラウザでPRをマージした日 その日のうちに git pull 枝分かれを防ぐ唯一の対策
新しいファイルを置いたとき 機密が含まれないか確認してから commit 履歴からは消せないため
PRを出したとき 数日以内に処理する。無理なら閉じる 放置すると前提が古くなる
月に1回 リポジトリが private のままか確認 設定は事故で変わりうる
最小構成

全部覚えられなくても、この1つだけ習慣にしてください。

週に1回、これを打つ
git status

何も変えないので、いつ打っても安全です。 出力の意味がわからなければ、そのままAIに貼り付けて 「これはどういう状態？ どうすべき？」と聞けば済みます。

用語辞典

repository / repo
リポジトリ　1つのプロジェクトの保管庫。フォルダ1つ＝リポジトリ1つ。
commit
コミット　「この時点」の記録。PC内に刻まれる。まだ外には出ていない。
push / pull
プッシュ／プル　GitHubへ送る／GitHubから取り込む。方向が逆なだけ。
branch
ブランチ　作業の分身。本編を汚さずに実験するための別冊。
main / master
メイン　本編にあたるブランチの名前。masterは古い呼び方で、意味は同じ。
merge
マージ・統合　別冊を本編に取り込む。両方の変更が残る。
conflict
コンフリクト・衝突　同じ行を両側が書き換えていて、Gitが判断できない状態。--abort で戻せる。
pull request / PR
プルリクエスト　「取り込んでいいですか」の申請書。merge＋確認画面＋記録。
origin
オリジン　送り先のGitHubリポジトリに付けられた既定の呼び名。「向こう側」の意味。
clone
クローン　GitHubにある倉庫を、まるごとPCに持ってくること。別のPCで作業を続けるときに使う。
.gitignore
ギットイグノア　記録しないものの一覧。これから追加するファイルにしか効かない。
staging
ステージング　add して commit を待っている状態。「記録対象に選ばれた」段階。
HEAD
ヘッド　今いる場所を指す印。「現在開いているページ」のようなもの。
hash（8d365e7 のような文字列）
ハッシュ　コミット1件ごとの固有ID。日付と役割はカルテの受付番号に近い。

Gitは「消さずに積む」道具です。カルテと同じで、書き足すことはできても、 書いたことをなかったことにはできません。 だからこそ入れる前に確認する——それさえ守れば、 あとは失敗しても取り返せます。

勉強会で使う場合は スライド版（全32枚） があります。
